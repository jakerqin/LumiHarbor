# 移动端上传

路由：[`app/(main)/mobile-upload/page.tsx`](../../app/(main)/mobile-upload/page.tsx)

## 职责边界

- **负责**：手机在局域网内快速选素材上传入库；上传时可选归入相册（新建/已有）；进度展示；失败重试；跨会话跳过已上传成功的文件
- **不负责**：素材浏览/管理（回到 [素材库](./07-素材库.md)）；公网访问、断点续传/分片上传、后台自动同步

页面本身**没有设备判断**，桌面浏览器打开同样能完整用（选文件、上传、相册关联逻辑一致）；只是布局按手机窄屏做的（`max-w-xl` 居中窄列 + 大触摸按钮），桌面大屏打开会两边留白，不是桌面级布局。路由命名用 `mobile-upload` 而不是通用的 `upload`，就是为了避免和「移动端优先」这个定位产生歧义——它不是要取代 [素材库](./07-素材库.md) 里桌面端的批量上传弹窗。

## 为什么单独做一个页面，而不是复用 `/assets` 的上传弹窗

- `DockNavigation` 靠 `mousemove` 显示/隐藏（见 [布局与导航](./05-布局与导航.md)），触屏设备没有 `mousemove`，导航永远不出现——移动页面必须**独立自足**，有自己的返回入口。
- 桌面 `UploadAssetsModal` 走一次性 `POST /ingestion/upload/batch`：整批成功或整批失败/超时，拿不到文件级状态，无法做「进度条」和「跳过已成功/只重传失败」。移动端场景（旅行几天、几十到上百个文件，Wi‑Fi 不一定稳）必须要有更细的颗粒度，所以改为**逐文件上传的客户端队列**。

## 核心数据流

```text
手机 Safari 打开 /mobile-upload（同 Wi-Fi）
        │
        ▼
MobileAssetPicker：<input multiple accept="image/*,video/*"> 多选
        │  每个文件算签名 `${name}_${size}_${lastModified}`
        ▼
useMobileUploadQueue.addFiles：命中 localStorage 已传签名 → 标记 skipped（不占用上传）
        │
        ▼
AlbumTargetSection：不选 / 新建相册 / 选已有相册（上传开始后锁定）
ShootLocationField：可选拍摄地点（MapPicker，上传开始后锁定）
        │
        ▼
点击“开始上传” → 队列串行执行 pending 项
  for item in pending:
    ingestionApi.uploadSingleAsset(item.file, { album, locationData, onProgress })
      POST /ingestion/upload（单文件；可选 default_gps / location_poi；超时 10 分钟）
        │
        ▼
    成功 → 写入 localStorage 签名；item.status = success
      若响应带 album（新建成功）→ 队列内部把后续/重试目标切到 {mode:'existing', albumId}
    失败 → item.status = failed，继续下一个（不中断队列）
        │
        ▼
完成态：成功/跳过/失败统计 + 「重试失败项」只重跑 failed 的 item + 关联相册链接
```

## 关键设计决策

### 为什么“已上传过自动跳过”只是启发式签名，不做真正的断点续传

真正的断点续传需要文件内容级校验（如分片哈希）与服务端配合，超出当前家用场景的成本收益比。用 `name+size+lastModified` 足以覆盖“同一批文件重新选择”的主流程；即使签名失效（换手机、文件被重新导出），服务端 SHA256 去重（见 [素材导入](../../../backend/docs/design/06-素材导入.md)）仍会兜底跳过，只是多花一次网络流量，不会产生重复素材。

### 为什么新建相册要等第一个文件成功后才“锁定” album_id

Upload 接口的“新建相册”每次调用都会真正创建一行（`AlbumService.get_or_create_album` 模式 B），如果每个文件都带着“新建”语义重试，会产生多个同名相册。队列约定：新建模式下只有第 1 个文件用 `mode:'new'`，成功后拿到 `album_id`，之后所有文件（含对第 1 个文件的重试）都切到 `mode:'existing'`。唯一没完全消除的竞态是“请求服务端已成功但客户端没收到响应”这种极端网络抖动导致的重试，概率低，本次接受（YAGNI），未引入后端幂等键。

### 为什么用单文件接口而不是 batch 接口

`/ingestion/upload/batch` 是整批一个请求，失败/超时无法定位到具体文件，也做不到单文件字节级进度。改成每个文件一个 `/ingestion/upload` 请求，配合前端串行队列，天然获得文件级状态与进度，代价是文件数多时请求数变多——对旅行量级（几十到上百个）可接受。

## 依赖

```text
/mobile-upload page
  → useMobileUploadQueue
      → ingestionApi.uploadSingleAsset → POST /ingestion/upload
  → MobileAssetPicker / AlbumTargetSection
      → albumsApi.getAlbums（搜索已有相册）
```

## 已知限制

- 仅局域网可用；出门时打不开（除非之后接 Tailscale 之类的组网）。
- “自动跳过”依赖 `localStorage`，仅同一部手机同一浏览器有效，见上文设计决策。
- 无大文件分片上传；单个视频传到一半断网只影响这一个文件（可重试），不影响其它已成功文件。
- 手机请用电脑局域网 IP 打开（如 `http://192.168.x.x:3000/mobile-upload`），不要用 `localhost`。
- API 根地址见 [`lib/api/baseUrl.ts`](../../lib/api/baseUrl.ts)：非本机访问时自动用「当前主机:8000」，避免仍打手机自己的 localhost。
- `npm run dev` 已带 `-H 0.0.0.0`，前后端需都在跑且防火墙放行 3000/8000。
- 桌面端 `UploadAssetsModal` / `ingestionApi.uploadAssets`（batch）未改动，仍受全局 10 秒 Axios 超时限制（见 [素材库已知限制](./07-素材库.md#已知限制)）；本页面的单文件上传单独放宽了超时，两条链路目前是独立的。
